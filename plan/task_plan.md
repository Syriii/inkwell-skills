# Inkwell 当前开发计划

## 目标

维护三个彼此独立、自包含、同时兼容 Codex 与 Claude Code 的技能：

| 技能 | 独立输入 | 独立输出 | 禁止依赖 |
|------|----------|----------|----------|
| `inkwell-capture` | URL、本地文件、截图或媒体 | 结构化 Markdown 与本地资源 | 不调用搜索或写作技能 |
| `inkwell-search` | 用户指定的 Markdown 目录或文本 | 本地索引、搜索或相似度结果 | 不假设内容来源或业务目录 |
| `inkwell-write` | 主题、文本、文件、链接或讨论记录 | 讨论、提纲与版本化文章 | 不要求索引或采集技能 |

## 已确定架构

- 三个技能平级独立，不是必须串联的管线。
- 技能不发现、安装、调用或要求兄弟技能。
- 用户或上层工作流可以显式把普通文件路径交给另一个技能；这只是文件互操作，不改变独立性。
- Codex/Claude 是单个技能的宿主兼容维度，不是三技能组合维度。
- 默认测试单位是“某一个技能单独安装在某一个宿主布局”；不设置三技能端到端任务测试。

## 下一步候选

以下项目均保持在各技能内部独立推进，不要求其他技能参与：

1. `inkwell-capture`：长图识别、分段 OCR、低置信度降级。
2. `inkwell-capture`：在具备 Python Playwright 的环境补跑专用 CLI 的 L2 分支。这是窄运行时验证，不是跨技能阶段。
3. `inkwell-capture`：煎蛋适配稳定后再评估通用论坛适配器接口。
4. `inkwell-search`、`inkwell-write`：只有出现新的真实使用问题时再分别优化。

## 术语禁区

- 不把“双宿主兼容”表述为“三技能端到端”。
- 不把普通 Markdown 互操作表述为自动调用或强制流程。
- 不因一个技能存在可选降级能力而推导出另一个 Inkwell 技能依赖。
- 未经用户明确提出上层组合需求，不重新讨论三技能联动架构。
